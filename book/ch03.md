> **Claim.** Three rules type the three nodes, and only the rule for a
> call can say no.

## A type is a promise about shape

Chapter 1's calculus accepts anything. `x x` is a term; so is a function
applied to itself applied to itself. A type is the promise that rules
some of that out before anything runs, and the simplest useful promise
is the one TypeScript makes about a function: it takes a `T` and returns
a `U`. Write that `T -> U` and call it the **arrow**. Two kinds of type
are enough for this chapter:

- a **base type** `A`, `B`: a name for a type we do not look inside;
- an arrow `T -> U`, which associates to the right: `A -> B -> C` is
  `A -> (B -> C)`, a function that takes an `A` and returns a function.

One node of the grammar grows a field: the binder now states its
argument type, `fun x : T => e`. With chapter 2's indices the name is
gone and the type stays, `fun : T => e`. Nothing else changes. This is
the *simply typed* lambda calculus, from 1940, and it is the smallest
system in which "this term has that type" is a question with a checkable
answer.

## The judgment

The question is written

$$\Gamma \vdash e : T$$

read "in context Γ, *e* has type *T*". The ⊢ symbol is called a
**turnstile**. The **context** Γ is the list of types of the binders
that have been opened on the way into *e*, one per free variable. With
indices it is a stack: the type of `#0` is on top, the type of `#1`
below it, and an index is a position in that stack. A closed term has an
empty context.

## Three rules

A typing rule is written as a fraction. Above the line are the premises;
below it is the conclusion; read the bar as "if everything above holds,
the thing below holds". A rule with nothing above the line is an axiom.
Three nodes, three rules [R: T-VAR](RULES.md#t-var) [R: T-LAM](RULES.md#t-lam) [R: T-APP](RULES.md#t-app):

$$\frac{\Gamma(i) = T}{\Gamma \vdash \#i : T}\ \text{VAR}
\qquad
\frac{\Gamma, T \vdash e : U}{\Gamma \vdash (\mathrm{fun} : T \Rightarrow e) : T \to U}\ \text{LAM}
\qquad
\frac{\Gamma \vdash f : T \to U \qquad \Gamma \vdash a : T' \qquad T' = T}{\Gamma \vdash f\ a : U}\ \text{APP}$$

VAR looks the index up. LAM pushes the argument type, types the body,
and wraps the result in an arrow. APP types both halves and then does
the one thing the other two never do: it compares. The argument's type
must equal the function's domain, and if it does not, there is no
conclusion. Every refusal in this chapter's checker is this comparison
failing. (VAR can also fail, but only on an index past the end of the
stack, which is an open term, not an ill-typed one.) The registry's
versions of these three rules are the ones chapter 4 reaches, where the
result type `U` may mention the argument; the arrow is the case where it
does not.

## A derivation, worked

Take `fun f : A -> B => fun x : A => f x` — "given a function and an
argument, apply it". With indices, `f` is `#1` and `x` is `#0` inside
the inner body. Build the tree from the leaves:

```text
   [A -> B, A](1) = A -> B          [A -> B, A](0) = A
   ----------------------- VAR      ------------------- VAR
   [A -> B, A] ⊢ #1 : A -> B        [A -> B, A] ⊢ #0 : A        A = A
   -------------------------------------------------------------------- APP
   [A -> B, A] ⊢ #1 #0 : B
   -------------------------------------------------------------------- LAM
   [A -> B] ⊢ (fun : A => #1 #0) : A -> B
   -------------------------------------------------------------------- LAM
   [] ⊢ (fun : A -> B => fun : A => #1 #0) : (A -> B) -> A -> B
```

Read it bottom-up and it is a search: to type the outer function, push
`A -> B` and type the body; to type that, push `A` and type the body; to
type the call, type both halves and compare. Read it top-down and it is
a proof that the conclusion holds. The checker's `infer` is the search
written as recursion, one case per node. The tree is its call stack.

The term is an old one: it is chapter 1's `1`, now with types attached.
The types also choose a reading. As *apply*, it takes any `A -> B`. As
the numeral, it has to apply `f` to its own output, so `B` must be `A`
and the type narrows to `(A -> A) -> A -> A`. The term did not change.
The annotation says which reading is meant, and the checker holds the
term to it.

Now `(fun x : A => x) y` where `y` has type `B`. VAR gives `y : B`, LAM
gives the function `A -> A`, and APP asks whether `B = A`. It does not.
There is no tree, and the checker says so. That is the first refusal in
this book, and everything that follows is more rules and more ways to
refuse.

## The line that grows

The comparison in APP is structural: two types are equal when they have
the same shape. That is the right answer here and the wrong answer three
chapters from now, when types contain programs and `2 + 3` has to equal
`5`. Chapter 5 builds the machinery that runs those programs and chapter
6 puts it behind the comparison, where it becomes half the kernel. Keep
an eye on `typeEq` below. It is one line in this chapter and it is the
line the rest of the book is about.

The exercise ends on chapter 2's three programs, each binder now carrying
a type. The identity and the constant function are accepted. The
self-applying term, the one that never stopped, is refused: for `x x` to
type, `x` would have to be an arrow and its own domain at once, and no
type is both. The first program a type takes away is the one that loops,
and it stays refused for the rest of the book.

## Try it

```ts
// Chapter 3 — The arrow.
// Three rules type three nodes, and only the rule for a call can say no.

type Type =
  | { kind: "base"; name: string } // A, B: a type we do not look inside
  | { kind: "arrow"; from: Type; to: Type }; // T -> U

type Expr =
  | { kind: "bvar"; idx: number } // #0 is the nearest binder (chapter 2)
  | { kind: "lam"; type: Type; body: Expr } // fun : T => body
  | { kind: "app"; fn: Expr; arg: Expr };

const base = (name: string): Type => ({ kind: "base", name });
const arrow = (from: Type, to: Type): Type => ({ kind: "arrow", from, to });
const bvar = (idx: number): Expr => ({ kind: "bvar", idx });
const lam = (type: Type, body: Expr): Expr => ({ kind: "lam", type, body });
const app = (fn: Expr, arg: Expr): Expr => ({ kind: "app", fn, arg });

function showT(t: Type): string {
  return t.kind === "base" ? t.name : `(${showT(t.from)} -> ${showT(t.to)})`;
}
function show(e: Expr): string {
  switch (e.kind) {
    case "bvar":
      return `#${e.idx}`;
    case "lam":
      return `(fun : ${showT(e.type)} => ${show(e.body)})`;
    case "app":
      return `(${show(e.fn)} ${show(e.arg)})`;
  }
}

// Two types are equal when they have the same shape. Chapter 6 replaces
// this one function with the half of the kernel that runs programs.
function typeEq(a: Type, b: Type): boolean {
  if (a.kind === "base" && b.kind === "base") return a.name === b.name;
  if (a.kind === "arrow" && b.kind === "arrow") return typeEq(a.from, b.from) && typeEq(a.to, b.to);
  return false;
}

// The context is a stack of types: ctx[0] is the type of #0.
type Ctx = Type[];
type Verdict = { ok: true; type: Type } | { ok: false; reason: string };

function infer(ctx: Ctx, e: Expr): Verdict {
  switch (e.kind) {
    case "bvar": {
      // T-VAR: look the index up.
      const t = ctx[e.idx];
      return t === undefined ? { ok: false, reason: `#${e.idx} is not in scope` } : { ok: true, type: t };
    }
    case "lam": {
      // T-LAM: type the body with the argument pushed, then wrap.
      const body = infer([e.type, ...ctx], e.body);
      return body.ok ? { ok: true, type: arrow(e.type, body.type) } : body;
    }
    case "app": {
      // T-APP: the function must be an arrow, and its domain must match the argument.
      const f = infer(ctx, e.fn);
      if (!f.ok) return f;
      if (f.type.kind !== "arrow") return { ok: false, reason: `${showT(f.type)} is not a function type` };
      const a = infer(ctx, e.arg);
      if (!a.ok) return a;
      if (!typeEq(f.type.from, a.type)) {
        return { ok: false, reason: `argument has type ${showT(a.type)}, function wants ${showT(f.type.from)}` };
      }
      return { ok: true, type: f.type.to };
    }
  }
}

function report(ctx: Ctx, e: Expr): void {
  const v = infer(ctx, e);
  console.log(`${show(e)}  :  ${v.ok ? showT(v.type) : `refused — ${v.reason}`}`);
}

const A = base("A");
const B = base("B");

// fun f : A -> B => fun x : A => f x — the derivation the chapter worked.
report([], lam(arrow(A, B), lam(A, app(bvar(1), bvar(0)))));

// (fun x : A => x) y, with y : B in scope as #0. Only T-APP can refuse.
report([B], app(lam(A, bvar(0)), bvar(0)));

// Chapter 2's three programs, with a type on each binder. The first two
// are accepted. The third is the term that never stopped: for `x x` to
// type, x would need to be an arrow and its own domain at once, and no
// type is. The first program a type takes away is the one that loops.
report([], lam(A, bvar(0)));
report([], lam(A, lam(B, bvar(1))));
report([], lam(A, app(bvar(0), bvar(0))));

// To break it: delete the typeEq test in the app case and rerun. The
// refused line now prints a type for a term that hands a B to a function
// wanting an A. The checker did not crash; it lied. Every rule the rest
// of the book adds is one more place where exactly this can go wrong.

export {}; // keeps this file a self-contained module
```

Expected output:

```text
(fun : (A -> B) => (fun : A => (#1 #0)))  :  ((A -> B) -> (A -> B))
((fun : A => #0) #0)  :  refused — argument has type B, function wants A
(fun : A => #0)  :  (A -> A)
(fun : A => (fun : B => #1))  :  (A -> (B -> A))
(fun : A => (#0 #0))  :  refused — A is not a function type
```
