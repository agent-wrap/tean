## The object under study

A proof assistant is a large program: an editor, an elaborator, a tactic
engine, a compiler. Almost none of it has to be correct. At the bottom sits
one small component, the **kernel**, and the whole system is arranged so
that only the kernel has to be right. Everything above it may produce
garbage, because everything above it must pass its output through the
kernel, and the kernel checks.

That design is only honest if the kernel is small enough to read. This book
builds one, and the first fact about it is the subject of this chapter: the
kernel is a function. It takes data in and returns a verdict. It performs
no I/O, holds no hidden state, and trusts nothing it did not compute
itself.

## A term is a tree

The data is called a **term** (the words *term* and *expression* are used
interchangeably). A term is a tree, and in TypeScript a tree is a
discriminated union. Five constructors are enough to start:

- a **sort**, written `Sort 0`, `Sort 1`, and so on — the types of types,
  which chapter 3 earns;
- a **constant** — a reference, by name, to something already checked;
- an **application** `f a`;
- a **function** `fun x : T => b`, called a *lambda*;
- a **function type** `(x : T) -> B`, called a *pi* (a historical name,
  from Π-types).

There is deliberately nothing else. No proof is a special kind of object: a
proof is a term, its statement is another term, and "this term proves that
statement" is a relation between two trees. The formal notation for that
relation, which the whole book computes, is:

$$\Gamma \vdash e : \alpha$$

read "in context Γ, the term *e* has type α" (the ⊢ symbol is called a
turnstile). The context Γ lists the variables in scope with their types; a
closed term has an empty context. The notation is the compressed form of
things you will hold in your hands first: a type you can paste into a
playground, a function you can run — then the rule the two of them
compress.

## A declaration is a named term

Terms arrive at the kernel packaged as **declarations**: a name, a stated
type, and — for a definition — a value. The two central well-formedness
rules are already visible at this altitude:

- the stated type must itself check, and its own type must be a sort —
  a "type" whose type is not a sort is data in the wrong position
  [R: WF-DECL-TYPE](RULES.md#wf-decl-type);
- the value, when present, must have the stated type [R: WF-DEF-VAL](RULES.md#wf-def-val).

The bracketed tags are rule citations: each names an entry in the book's
rule registry, collected in plain English in [the rules
appendix](RULES.md), and the build verifies every citation against the
published theory and two implementations. On a first read, treat them as
footnotes.

The checked declarations accumulate in the **environment**, a map from
names to declarations. The environment only grows, one verdict at a time,
and a name may enter it once — a second declaration under an old name is
refused outright [R: WF-NAME-FRESH](RULES.md#wf-name-fresh). Chapter 11 shows a file that attacks
exactly that rule.

## The whole trade in one signature

```
check : (Environment, Declaration) -> Verdict
```

Everything this book builds lives behind that signature. The next six
chapters fill in the function body: variables (chapter 2), universes
(chapter 3), computation (chapter 4), the two-function core (chapter 5),
data types (chapter 6), and recursion (chapter 7). The five chapters after
that point the finished function at input written by adversaries and
measure what happens.

One consequence of "pure function" deserves its own sentence: a checker
cannot be argued with. It cannot be lobbied, configured, or reassured. The
only way to change its verdict is to change the data — and that is the
entire value of the artifact.

## Try it

```ts
// Chapter 1 — A proof is data.
// A term is a tree. A checker is a function over that tree.
// Paste this whole file into any TypeScript playground and run it.

type Expr =
  | { kind: "sort"; level: number } // a universe: Sort 0, Sort 1, ...
  | { kind: "const"; name: string } // a reference to the environment
  | { kind: "app"; fn: Expr; arg: Expr } // f a
  | { kind: "lam"; binder: string; type: Expr; body: Expr } // fun x : T => b
  | { kind: "pi"; binder: string; type: Expr; body: Expr }; // (x : T) -> B

// One declaration: a name, a stated type, and (for a definition) a value.
interface Declaration {
  name: string;
  type: Expr;
  value?: Expr;
}

// The environment is everything checked so far.
type Environment = Map<string, Declaration>;

// The whole trade in one signature. No I/O, no state, no trust:
// data goes in, a verdict comes out.
type Verdict = { ok: true } | { ok: false; reason: string };
declare function check(env: Environment, d: Declaration): Verdict;

// A term is just a value. Here is `fun x : Nat => f x` as data:
const sample: Expr = {
  kind: "lam",
  binder: "x",
  type: { kind: "const", name: "Nat" },
  body: {
    kind: "app",
    fn: { kind: "const", name: "f" },
    arg: { kind: "const", name: "x" },
  },
};

function size(e: Expr): number {
  switch (e.kind) {
    case "sort":
    case "const":
      return 1;
    case "app":
      return 1 + size(e.fn) + size(e.arg);
    case "lam":
    case "pi":
      return 1 + size(e.type) + size(e.body);
  }
}

function show(e: Expr): string {
  switch (e.kind) {
    case "sort":
      return `Sort ${e.level}`;
    case "const":
      return e.name;
    case "app":
      return `(${show(e.fn)} ${show(e.arg)})`;
    case "lam":
      return `(fun ${e.binder} : ${show(e.type)} => ${show(e.body)})`;
    case "pi":
      return `((${e.binder} : ${show(e.type)}) -> ${show(e.body)})`;
  }
}

console.log(show(sample));
console.log(`nodes: ${size(sample)}`);

// To break it: add a new kind to Expr, say `lit`. The two switch
// statements stop compiling until you handle it. That compile error is
// the chapter's claim in miniature: a checker is total over its syntax,
// and the type system refuses a checker that forgot a case.

export {}; // keeps this file a self-contained module
```

Expected output:

```text
(fun x : Nat => (f x))
nodes: 5
```
