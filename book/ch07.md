> **Claim.** The kernel must verify an inductive declaration; it may never
> simply accept one.

## New types from outside

Everything so far was fixed grammar. An **inductive type** is different:
the input file *declares* one — a name, some **constructors**, their
types — and the kernel is being asked to extend its own logic with it. (A
constructor here is a way of building a member of the type, not a case
of a TypeScript union; the word changes sense at this chapter and keeps
the new one.) Natural numbers arrive this way: a type with constructors
`zero` and `succ : t -> t`. So does equality: `Eq` takes a type and two
of its members, and its one constructor, `refl`, proves `Eq a a` and
nothing else — a proof of `Eq a b` can exist only when `a` and `b` are
the same, which is the whole content of the type. And so does falsehood
(the inductive type with no constructors at all: nothing builds a member
of it, which is what makes it false).

Declaring numbers is a step past chapter 1, which encoded them. The
exercise in chapter 5 has `two = fun f => fun x => f (f x)`, a function
that only means two to a reader who expects it to. `succ (succ zero)` is
data: the kernel knows it was built from `zero` by two `succ`s, and can
take it apart case by case. Induction, the thing a proof about numbers
needs, works on the declared numbers and not on the encoded ones.
Chapter 9 builds the machinery that takes them apart.

That makes the declaration a contract, and the kernel reviews every
clause before signing [R: WF-IND-SPEC](RULES.md#wf-ind-spec).

## Telescopes, parameters, indices

Each constructor's type is a **telescope**: a chain of binders, each type
free to mention the variables before it, ending in the declared type
applied to some arguments. Drawn out, with the length-indexed vector
whose `cons` builds a vector one longer than its argument:

```text
   cons :  (A : Type) -> (n : Nat) -> (head : A) -> (tail : Vec A n) -> Vec A (n+1)
           '-----------------------------------------------------'    '----------'
                   the telescope: binders, each seeing the ones             the result:
                   before it (`tail`'s type mentions A and n)               the declared
                                                                            type, applied
```

The arguments in that result split into two kinds, and the difference
matters in chapter 9:

- **parameters** are fixed across the whole declaration. A list's element
  type is a parameter: every constructor returns a list of the *same*
  elements, so `A` above never varies.
- **indices** vary per constructor. The vector's length is an index: the
  result says `n+1` while the recursive argument said `n`. An index is
  what a constructor is allowed to *change*.

The contract also requires that parameters agree across every type of a
**mutual declaration** — several types declared together, allowed to
mention each other — and that all types of the block live in one
universe.

Two clauses are famous enough to carry their own names.

## Positivity

A constructor argument may *use* the type being declared — that is what
recursion is — but only in positive position: as the result of the
argument's type, never to the left of an arrow [R: WF-IND-POS](RULES.md#wf-ind-pos). The
forbidden shape is `mk : (t -> Bool) -> t`.

You can write that shape today. TypeScript accepts
`type Bad = (x: Bad) => boolean` without comment, and will happily take
`const notMe: Bad = (x) => !x(x)` — Cantor's diagonal, spelled in a
language you already use. The difference is what the two type systems
promise. TypeScript's job is to stop you crashing, and `notMe(notMe)`
does not crash; it hangs. A kernel's job is to stop you *proving* things,
and the same construction, run in a logic, is a proof of falsehood: the
constructor hands every element of `t` a function out of `t`, which
injects the function space of `t` into `t`, and the diagonal turns the
injection into a contradiction. The positivity check is about thirty
lines, and it is the whole distance between a hang and a theorem. The
exercise below implements it, and then writes `notMe` in TypeScript
beside it.

## The universe bound

Each constructor argument's type lives in some universe `Sort l'`, and the
declared type lives in `Sort l`. The contract requires
`imax(l', l) <= l` [R: WF-IND-UNIV](RULES.md#wf-ind-univ): a constructor must not smuggle a
bigger universe into a smaller box, or the ladder of chapter 4 collapses
by the back door. The imax (chapter 4's absorbing operation) is what
still lets a *proposition* quantify over anything.

That is the rule as the theory states it; a kernel implements the same
condition as two cheaper tests — *is `l` at least `l'`, or does `l`
normalize to zero?* The two agree by the imax definition. If `l` is zero
then `imax(l', 0) = 0 <= 0` holds always, which is the second test; and
if `l` is a successor then `imax(l', l) = max(l', l)`, and
`max(l', l) <= l` exactly when `l' <= l`, which is the first. A reader
diffing the book against a kernel will meet the second form, and it is
chapter 4's imax semantics doing the work in both.

One more clause limits not what a type stores but what it can *compute*:
a proposition with real alternatives — two constructors, or a data-bearing
field — may only eliminate into Prop [R: WF-LARGE-ELIM](RULES.md#wf-large-elim) ("eliminate into a
universe": let the pattern-matching principle chapter 9 derives build its
results there). Chapter 6's proof irrelevance declared all proofs of such
a proposition equal; letting a Bool-valued function distinguish them would
contradict that on the spot. The narrow exception — one constructor, with
every field forced by the result type — is called a **subsingleton**: the
type's own shape already says which element you have, so no information
can leak out of it. Subsingletons return with consequences in chapter 10.

## Try it

```ts
// Chapter 7 — Data types are contracts.
// The positivity check, on constructor argument types.

// A constructor argument type, simplified to what the check inspects:
type ArgType =
  | { kind: "self" } // the type being declared, applied to its params
  | { kind: "other"; name: string } // any established type
  | { kind: "arrow"; from: ArgType; to: ArgType }; // a function type

const self: ArgType = { kind: "self" };
const other = (name: string): ArgType => ({ kind: "other", name });
const arrow = (from: ArgType, to: ArgType): ArgType => ({ kind: "arrow", from, to });

function mentionsSelf(t: ArgType): boolean {
  switch (t.kind) {
    case "self":
      return true;
    case "other":
      return false;
    case "arrow":
      return mentionsSelf(t.from) || mentionsSelf(t.to);
  }
}

// Strict positivity: the type being declared may appear as the RESULT of
// an argument's type, but never to the LEFT of an arrow inside it.
function isPositive(t: ArgType): boolean {
  if (!mentionsSelf(t)) return true; // nonrecursive argument: fine
  switch (t.kind) {
    case "self":
      return true; // a plain recursive argument: fine
    case "other":
      return true;
    case "arrow":
      // The domain must not mention the type at all; recurse on the result.
      return !mentionsSelf(t.from) && isPositive(t.to);
  }
}

function show(t: ArgType): string {
  switch (t.kind) {
    case "self":
      return "t";
    case "other":
      return t.name;
    case "arrow":
      return `(${show(t.from)} -> ${show(t.to)})`;
  }
}

function verdict(ctor: string, args: ArgType[]): void {
  const bad = args.find((a) => !isPositive(a));
  const v = bad === undefined ? "accepted" : `refused: ${show(bad)} is not positive`;
  console.log(`${ctor.padEnd(34)} ${v}`);
}

// Nat:  zero : t          succ : t -> t  (argument type is `self`)
verdict("succ (arg: t)", [self]);
// Rose tree: node : (Nat -> t) -> t — self on the RIGHT of the arrow: ok.
verdict("node (arg: Nat -> t)", [arrow(other("Nat"), self)]);
// The forbidden shape: mk : (t -> Bool) -> t — self on the LEFT.
verdict("mk (arg: t -> Bool)", [arrow(self, other("Bool"))]);
// Hidden one level deeper, still caught:
verdict("mk2 (arg: (t -> Bool) -> Nat)", [arrow(arrow(self, other("Bool")), other("Nat"))]);

// Now the same shape in the type system you already use. TypeScript has
// no positivity rule, because a type system that only has to not crash
// does not need one:
type Bad = (x: Bad) => boolean;
const notMe: Bad = (x) => !x(x); // Cantor's diagonal, written out
console.log(`\nTypeScript accepts   type Bad = (x: Bad) => boolean`);
console.log(`and with it           notMe = (x) => !x(x)   : ${typeof notMe}`);
console.log(`notMe(notMe) does not terminate, so it is never called here.`);

// To break it: accept `mk : (t -> Bool) -> t` and follow the arithmetic.
// Each element of t now carries a function t -> Bool. That gives an
// injection from functions-out-of-t into t itself, and Cantor's diagonal
// builds the impossible member out of it — exactly the `notMe` above. In
// a programming language that is a hang; in a proof assistant it is a
// provable False. Chapter 14 runs this attack against the real checker,
// twice: once refused, once with the rule off.

export {}; // keeps this file a self-contained module
```

Expected output:

```text
succ (arg: t)                      accepted
node (arg: Nat -> t)               accepted
mk (arg: t -> Bool)                refused: (t -> Bool) is not positive
mk2 (arg: (t -> Bool) -> Nat)      refused: ((t -> Bool) -> Nat) is not positive

TypeScript accepts   type Bad = (x: Bad) => boolean
and with it           notMe = (x) => !x(x)   : function
notMe(notMe) does not terminate, so it is never called here.
```
