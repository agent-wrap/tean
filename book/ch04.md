> **Claim.** One grammar holds terms and types both, and the universe
> ladder is what keeps that from collapsing.

## Three more nodes

Chapter 3 gave the binder its type. Three nodes join the grammar here:

- a **sort**, written `Sort 0`, `Sort 1`, and so on — the types of types,
  which this chapter is about;
- a **function type** `(x : T) -> B`, called a *pi* (a historical name,
  from Π-types): the type of a function whose argument is named `x`,
  because `B` may mention it. Chapter 3's arrow `T -> U` is the case
  where `B` does not mention `x`, and the book keeps writing that case
  as an arrow;
- a **constant** — a reference, by name, to something already checked.

The constant node needs something to refer to. Terms arrive at the kernel
packaged as **declarations**: a name, a stated type, and — for a
definition — a value. Two well-formedness rules are already visible:

- the stated type must itself check, and its own type must be a sort — a
  "type" whose type is not a sort is data in the wrong position
  [R: WF-DECL-TYPE](RULES.md#wf-decl-type);
- the value, when present, must have the stated type
  [R: WF-DEF-VAL](RULES.md#wf-def-val).

The bracketed tags are rule citations: each names an entry in the book's
rule registry, collected in plain English in [the rules
appendix](RULES.md), and the build verifies every citation against the
published theory and two implementations. On a first read, treat them as
footnotes.

The checked declarations accumulate in the **environment**, a map from
names to declarations. The environment only grows, one verdict at a time,
and a name may enter it once — a second declaration under an old name is
refused outright [R: WF-NAME-FRESH](RULES.md#wf-name-fresh). Chapter 14
shows a file that attacks exactly that rule. A constant is a lookup in
that map. A free variable, in chapter 1's sense, is what a constant is
not: a name the environment has never heard of, whose type the context
Γ of chapter 3 supplies instead. Every symbol the book uses is collected
on one page, [the notation card](NOTATION.md), with how to say it out
loud and which chapter owns it.

So the whole trade, in one signature:

```
check : (Environment, Declaration) -> Verdict
```

Everything this book builds lives behind it. Chapters 5 to 10 fill in the
function body; the five after that point the finished function at input
written by adversaries and measure what happens. One consequence of "pure
function" deserves its own sentence: a checker cannot be argued with. It
cannot be lobbied, configured, or reassured. The only way to change its
verdict is to change the data — and that is the entire value of the
artifact. Twenty-six independent reimplementations of the kernel this
book follows exist, every one of them behind this signature.

## One grammar

In the system this book checks, a type is not a separate species. The type
of a term is another term, and that term has a type too. `fun x : T => x`
has type `(x : T) -> T`, which has type `Sort 1`, which has type `Sort 2`.
The nodes called sorts are where the regress is organized: `Sort 0`,
abbreviated **Prop**, holds propositions; `Sort 1`, abbreviated **Type**,
holds ordinary data types; `Sort (l+1)` holds `Sort l` [R: T-SORT](RULES.md#t-sort).

The word *proposition* is doing work there. In this system a proposition
is a type, and a proof of it is a term of that type: `p : Prop` is a
statement, `h : p` is evidence for it, and the evidence is checked by the
same three rules chapter 3 ran on `f x`. That identification —
propositions as types, proofs as terms — is the **Curry–Howard
correspondence**, and it is the reason a proof checker and a type checker
are one program. It is not a metaphor: chapter 6 treats two proofs of one
proposition as interchangeable, and that is a rule about terms.

Chapter 3's worked tree is the smallest example. Read `A` and `B` as
propositions and `(A -> B) -> A -> B` says: if A implies B, and A holds,
then B holds. That is modus ponens, and the derivation that typed
`fun f => fun x => f x` is its proof. This is the third reading chapter 1
promised for that term.

TypeScript has the bottom two rungs of this ladder and stops. `number` is
a type; `Array` is not — it is something that *makes* a type when you
hand it one, and TypeScript gives you no way to write down what `Array`
itself is, or to quantify over all such things. Here you can: `Array` is
an ordinary term whose type is `Type -> Type`, that type is a term whose
type is `Sort 2`, and the ladder keeps going. One grammar all the way up
is what buys that.

Why not stop the regress with `Sort : Sort`? Because that one equation
makes the system inconsistent: Girard's paradox builds, inside any such
system, a well-typed term proving falsehood — the type-theory rendering of
"the set of all sets that do not contain themselves". The ladder is not
bureaucracy. It is the fix, and it has to go all the way up.

## Levels are a little language

The rung numbers, called **levels**, form their own small grammar: zero, a
successor `l+1`, a maximum `max(l1, l2)`, a variable (so a declaration can
be level-polymorphic — one definition usable at every rung), and one
strange operation, `imax`:

$$\mathrm{imax}(l, 0) = 0 \qquad \mathrm{imax}(l, m+1) = \max(l, m+1)$$

Because levels contain variables, equality of levels is not equality of
numbers. The kernel decides it syntactically: normalize both sides —
flatten the maxes, sort the operands, drop dominated entries — and compare
[R: LVL-NORM](RULES.md#lvl-norm). Beside it sits a separate *inequality*
judgment — a relation the checker decides — a syntactic descent through
max, imax, and numeric offsets [R: LVL-LEQ](RULES.md#lvl-leq). The
published theory specifies that inequality with a case split on every level
variable, trying it at zero and then at a successor; the kernel implements
the cheaper descent instead, which refuses some true inequalities and
accepts no false ones. Its one caller is the universe bound that chapter 7
puts on new data declarations. These two functions are fiddly, heavily
tested, and entirely mechanical; the interesting rule is the one that uses
imax.

## The pi rule, and why imax

A function type lives in the universe of its parts. The rule below is
chapter 3's LAM rule asked about a type rather than a term: read Γ, x:A
as the context Γ extended with *x* of type *A*, and read the conclusion
as the arrow with the level bookkeeping the arrow never needed:

$$\frac{\Gamma \vdash A : \mathrm{Sort}\ l_1 \qquad \Gamma, x{:}A \vdash B : \mathrm{Sort}\ l_2}{\Gamma \vdash (x:A) \to B\ :\ \mathrm{Sort}\ (\mathrm{imax}(l_1, l_2))}$$

[R: T-PI](RULES.md#t-pi) with [R: LVL-IMAX](RULES.md#lvl-imax) doing the work. Take the most ordinary
statement in mathematics: *for every number n, n + 0 = n* (the numbers
and the `=` are data types chapter 7 declares; take them on credit until
then). Its conclusion
is a proposition, so it belongs in Prop. Its domain is the numbers, which
are data and live one rung up. If the rule used `max`, the finished
statement would land in `Type` — and every theorem that quantifies over a
data type would stop being a proposition. `imax` says: if the *result* is
a proposition, the whole function type is a proposition, however large the
domain. Prop absorbs.

The same collapse is what lets a proposition quantify over *all*
propositions — `(p : Prop) -> p` stays in Prop rather than climbing out of
it. (That particular statement is often introduced as a definition of
falsehood. It is not one here: in this system `False` is declared, not
encoded, and chapter 7 is where declarations like it are checked.) The
technical name for the collapse is *impredicativity*, and it is confined
to Prop; the data-carrying rungs stay predicative, and chapter 7 shows the
rule that polices the border when data types are declared.

## The checker, one grammar

The exercise is chapter 3's checker with the grammar above in place of
two separate types. Three cases join `infer`, one per new node: a sort
has the next sort as its type [R: T-SORT](RULES.md#t-sort), a constant
is a lookup in the environment [R: T-CONST](RULES.md#t-const), and a
pi is the rule above, with `imax` on the two levels. Two old cases
change shape. LAM now returns a pi rather than an arrow, because the
body's type may mention the argument. APP, having matched the argument
against the domain, returns the pi's body *with the argument
substituted in*, and that one substitution is what the word
*dependent* means: `Eq Nat` is a type whose later arguments are
constrained by the earlier one, and the checker computes the
constraint by chapter 2's `instantiate`.

Equality is still chapter 3's `typeEq`, one case per node and
structural. The exercise types a theorem statement about numbers into
Prop, a quantifier over all propositions into Prop, a quantifier over
all types into `Sort 2`, and the identity for every type at once into
a pi whose body mentions `#0`. Chapter 2's three programs run again:
the self-applying term is refused here exactly as in chapter 3, and the
constant function on two arguments is typed but not run, because this
checker cannot run anything yet. Chapter 5 is where that becomes a
problem, and where `typeEq` is replaced.

The exercise's last line runs the rule with `max` in place of `imax`.
The wrong rule does not crash — it just quietly reclassifies ordinary
theorems out of Prop. A kernel bug of this kind refuses true theorems
rather than accepting false ones, and telling those two failure modes
apart becomes the organizing question of chapter 14.

## Try it

```ts
// Chapter 4 — Types are terms.
// Chapter 3's checker over one grammar: a type is a term, so the same
// `infer` types both, and the universe ladder keeps that from collapsing.

type Expr =
  | { kind: "bvar"; idx: number } // #0 is the nearest binder (chapter 2)
  | { kind: "sort"; level: number } // Sort 0 is Prop, Sort 1 is Type
  | { kind: "const"; name: string } // a name the environment has checked
  | { kind: "pi"; type: Expr; body: Expr } // (x : type) -> body; body may mention #0
  | { kind: "lam"; type: Expr; body: Expr } // fun x : type => body
  | { kind: "app"; fn: Expr; arg: Expr };

const bvar = (idx: number): Expr => ({ kind: "bvar", idx });
const sort = (level: number): Expr => ({ kind: "sort", level });
const cnst = (name: string): Expr => ({ kind: "const", name });
const pi = (type: Expr, body: Expr): Expr => ({ kind: "pi", type, body });
const lam = (type: Expr, body: Expr): Expr => ({ kind: "lam", type, body });
const app = (fn: Expr, arg: Expr): Expr => ({ kind: "app", fn, arg });

// Concrete levels are enough to see the shape (the real thing also has
// level variables, max, and a normalizer). imax collapses when the right
// side is zero: a family of propositions is a proposition, however big
// the domain. Flip the switch and the rule becomes plain max.
let useMaxInstead = false;
function imax(l1: number, l2: number): number {
  if (useMaxInstead) return Math.max(l1, l2);
  return l2 === 0 ? 0 : Math.max(l1, l2);
}

// The environment: names already checked, each with its stated type.
// Eq : (A : Type) -> A -> A -> Prop. Its body mentions its first argument,
// so with indices it is pi(Type, pi(#0, pi(#1, Prop))).
const env = new Map<string, Expr>([
  ["Nat", sort(1)], // Nat : Type
  ["zero", cnst("Nat")], // zero : Nat
  ["succ", pi(cnst("Nat"), cnst("Nat"))], // succ : Nat -> Nat
  ["Eq", pi(sort(1), pi(bvar(0), pi(bvar(1), sort(0))))],
]);

// Chapter 2's two moves, with a case for each binder.
function lift(e: Expr, start: number, amount: number): Expr {
  switch (e.kind) {
    case "bvar":
      return e.idx >= start ? bvar(e.idx + amount) : e;
    case "app":
      return app(lift(e.fn, start, amount), lift(e.arg, start, amount));
    case "lam":
      return lam(lift(e.type, start, amount), lift(e.body, start + 1, amount));
    case "pi":
      return pi(lift(e.type, start, amount), lift(e.body, start + 1, amount));
    default:
      return e;
  }
}

function instantiate(e: Expr, a: Expr, depth = 0): Expr {
  switch (e.kind) {
    case "bvar":
      if (e.idx === depth) return lift(a, 0, depth);
      return e.idx > depth ? bvar(e.idx - 1) : e;
    case "app":
      return app(instantiate(e.fn, a, depth), instantiate(e.arg, a, depth));
    case "lam":
      return lam(instantiate(e.type, a, depth), instantiate(e.body, a, depth + 1));
    case "pi":
      return pi(instantiate(e.type, a, depth), instantiate(e.body, a, depth + 1));
    default:
      return e;
  }
}

function show(e: Expr): string {
  switch (e.kind) {
    case "bvar":
      return `#${e.idx}`;
    case "sort":
      return e.level === 0 ? "Prop" : e.level === 1 ? "Type" : `Sort ${e.level}`;
    case "const":
      return e.name;
    case "pi":
      return `(${show(e.type)} -> ${show(e.body)})`;
    case "lam":
      return `(fun : ${show(e.type)} => ${show(e.body)})`;
    case "app":
      return `(${show(e.fn)} ${show(e.arg)})`;
  }
}

// Chapter 3's typeEq, one case per node. Still structural: two types are
// equal when they are the same tree. Chapter 5 is about why that is not
// enough once a type can contain a program.
function typeEq(a: Expr, b: Expr): boolean {
  if (a.kind !== b.kind) return false;
  switch (a.kind) {
    case "bvar":
      return a.idx === (b as { idx: number }).idx;
    case "sort":
      return a.level === (b as { level: number }).level;
    case "const":
      return a.name === (b as { name: string }).name;
    case "app": {
      const bb = b as { fn: Expr; arg: Expr };
      return typeEq(a.fn, bb.fn) && typeEq(a.arg, bb.arg);
    }
    case "pi":
    case "lam": {
      const bb = b as { type: Expr; body: Expr };
      return typeEq(a.type, bb.type) && typeEq(a.body, bb.body);
    }
  }
}

// ctx[i] is the type of #i, recorded at its binder: lift it past the
// i + 1 binders crossed since, because a type may now mention a variable.
type Ctx = Expr[];
type Verdict = { ok: true; type: Expr } | { ok: false; reason: string };

// A level, or the reason the term is not a type.
function ensureSort(v: Verdict): { ok: true; level: number } | { ok: false; reason: string } {
  if (!v.ok) return v;
  if (v.type.kind !== "sort") return { ok: false, reason: `${show(v.type)} is not a sort, so this is not a type` };
  return { ok: true, level: v.type.level };
}

function infer(ctx: Ctx, e: Expr): Verdict {
  switch (e.kind) {
    case "bvar": {
      // T-VAR, as in chapter 3, plus the lift.
      const t = ctx[e.idx];
      return t === undefined ? { ok: false, reason: `#${e.idx} is not in scope` } : { ok: true, type: lift(t, 0, e.idx + 1) };
    }
    case "sort":
      // T-SORT: the ladder. Sort l : Sort (l + 1).
      return { ok: true, type: sort(e.level + 1) };
    case "const": {
      // T-CONST: a lookup in the environment.
      const t = env.get(e.name);
      return t === undefined ? { ok: false, reason: `${e.name} is not in the environment` } : { ok: true, type: t };
    }
    case "pi": {
      // T-PI: both halves must be types, and the result lives at imax.
      const l1 = ensureSort(infer(ctx, e.type));
      if (!l1.ok) return l1;
      const l2 = ensureSort(infer([e.type, ...ctx], e.body));
      if (!l2.ok) return l2;
      return { ok: true, type: sort(imax(l1.level, l2.level)) };
    }
    case "lam": {
      // T-LAM, as in chapter 3, but the domain must be a type, and the
      // result is a pi, because the body's type may mention the argument.
      const dom = ensureSort(infer(ctx, e.type));
      if (!dom.ok) return dom;
      const body = infer([e.type, ...ctx], e.body);
      return body.ok ? { ok: true, type: pi(e.type, body.type) } : body;
    }
    case "app": {
      // T-APP, as in chapter 3, and then the one new move: the result is
      // the pi's body with the argument substituted in. That is dependency.
      const f = infer(ctx, e.fn);
      if (!f.ok) return f;
      if (f.type.kind !== "pi") return { ok: false, reason: `${show(f.type)} is not a function type` };
      const a = infer(ctx, e.arg);
      if (!a.ok) return a;
      if (!typeEq(f.type.type, a.type)) {
        return { ok: false, reason: `argument has type ${show(a.type)}, function wants ${show(f.type.type)}` };
      }
      return { ok: true, type: instantiate(f.type.body, e.arg) };
    }
  }
}

function report(label: string, e: Expr): void {
  const v = infer([], e);
  console.log(`${label.padEnd(34)} : ${v.ok ? show(v.type) : `refused — ${v.reason}`}`);
}

const Nat = cnst("Nat");
const Eq = cnst("Eq");

// The everyday case: a statement about numbers must still be a statement.
// Nat : Type, so the domain sits at level 1; the body is a Prop, level 0.
report("(n : Nat) -> Eq Nat n n", pi(Nat, app(app(app(Eq, Nat), bvar(0)), bvar(0))));

// Quantifying over ALL propositions lands back in Prop: impredicativity.
report("(p : Prop) -> p", pi(sort(0), bvar(0)));

// A quantifier over Type climbs: the domain is at level 2, the body at 1.
report("(A : Type) -> A", pi(sort(1), bvar(0)));

// A term whose type is a dependent pi: the identity for every type at once.
report("fun A : Type => fun x : A => x", lam(sort(1), lam(bvar(0), bvar(0))));

// The three programs, now typed. The judge of chapter 6 will agree.
report("fun x : Nat => x", lam(Nat, bvar(0)));
report("fun x : Nat => fun y : Nat => x", lam(Nat, lam(Nat, bvar(1))));
report("K zero (succ zero)", app(app(lam(Nat, lam(Nat, bvar(1))), cnst("zero")), app(cnst("succ"), cnst("zero"))));
report("fun x : Nat => x x", lam(Nat, app(bvar(0), bvar(0))));

// With max instead of imax, Prop stops absorbing:
useMaxInstead = true;
report("(n : Nat) -> Eq Nat n n, with max", pi(Nat, app(app(app(Eq, Nat), bvar(0)), bvar(0))));

// To break it: that last line IS the break. A kernel whose pi rule uses
// max instead of imax says that a theorem about numbers lives in Type,
// not Prop — every theorem that quantifies over a data type stops being
// a proposition, and the chapter 6 rule that makes any two proofs of a
// proposition interchangeable no longer applies to any of them.
// The dual mistake — letting Sort l : Sort l — accepts everything,
// including a proof of False, by Girard's paradox. The ladder is not
// decoration; it is the wall between those two failures.

export {}; // keeps this file a self-contained module
```

Expected output:
